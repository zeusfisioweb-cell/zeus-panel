## CRITICAL

### C1 · `window.confirm()` en desvincular cuenta portal — CORREGIDO

**Archivo:** `src/app/(admin)/pacientes/components/PatientDetailsPanel.tsx:184`  
**Flujo:** Pacientes → Ficha → Datos → "Desvincular cuenta portal"

**Problema:** `handleUnlinkPortal` usaba `if (!confirm('...')) return`. El diálogo nativo del browser:
- Se bloquea silenciosamente en Safari/iOS y en iframes (Vercel Preview, cualquier embed).
- No puede ser interactuado por Playwright sin `page.on('dialog', ...)`.
- UX inconsistente: diálogo gris del OS dentro de una UI custom.

**Fix aplicado:**
- Renombrada función a `doUnlinkPortal` (ejecuta el fetch directamente).
- Añadido estado `showUnlinkConfirm: boolean`.
- El botón abre `showUnlinkConfirm = true`.
- Se renderiza `<ConfirmModal variant="warning" ...>` (ya existente en `src/components/ConfirmModal.tsx`) que confirma antes de llamar `doUnlinkPortal()`.
- Nodo Fragment añadido al return para acomodar modal fuera del drawer.

### C2 · Overlap check en dashboard usa siempre citas de HOY — CORREGIDO

**Archivo:** `src/app/(admin)/page.tsx:106-115`  
**Flujo:** Dashboard → date-picker → seleccionar mañana → "Nueva cita" → crear con profesional X

**Problema:** `useMemo` con deps `[]` → `todayIso`/`tomorrowIso` eran constantes que siempre apuntaban a hoy. `useCitas(todayIso, tomorrowIso)` solo cargaba citas de hoy. Si el usuario creaba una cita para otro día, el overlap check usaba datos de hoy → doble-booking posible para cualquier fecha ≠ hoy.

```tsx
// ANTES — deps vacío, siempre hoy
const { todayIso, tomorrowIso } = useMemo(() => {
    const today = DateTime.now().setZone(CLINIC_TIME_ZONE).startOf('day');
    return { todayIso: today.toISO() ?? '', tomorrowIso: today.plus({ days: 1 }).toISO() ?? '' };
}, []);
```

**Fix aplicado:**
- Renombrado a `selectedDayIso`/`nextDayIso`.
- `useMemo` ahora depende de `[selectedDate]`.
- `useCitas` carga citas del día seleccionado en el picker.
- `hasProfessionalOverlap` recibe `selectedDayAppointments`.

```tsx
// DESPUÉS — sigue selectedDate del picker
const { selectedDayIso, nextDayIso } = useMemo(() => {
    const day = DateTime.fromJSDate(selectedDate, { zone: CLINIC_TIME_ZONE }).startOf('day');
    return { selectedDayIso: day.toISO() ?? '', nextDayIso: day.plus({ days: 1 }).toISO() ?? '' };
}, [selectedDate]);
const { data: selectedDayAppointments = [] } = useCitas(selectedDayIso, nextDayIso);
```

## HIGH

### H1 · Race condition en búsqueda de paciente — CORREGIDO

**Archivo:** `src/app/(admin)/citas/components/AppointmentFormModal.tsx:148-165`  
**Flujo:** Nueva cita → campo "Buscar paciente" → escritura rápida

**Problema:** Debounce de 300 ms pero sin cancelación de requests previos. Escribiendo "A" → "An" → "Ana" se disparan 3 fetches en paralelo. Si el fetch de "A" (más lento por caché fría) llega después que "Ana", sobreescribe los resultados correctos con datos incorrectos.

**Fix aplicado:**
- Añadido `searchAbortRef = useRef<AbortController | null>(null)`.
- Antes de cada fetch: `searchAbortRef.current?.abort()` cancela el anterior.
- Nuevo `AbortController` creado y asignado a `searchAbortRef.current`.
- `fetch` recibe `signal: controller.signal`.
- Catch ignora `AbortError` (cancelación intencional); cualquier otro error sigue limpiando resultados.
- Cleanup del effect: `searchAbortRef.current?.abort()` al desmontar.

### H2 · `consentCount` KPI calculado solo de la página actual — CORREGIDO

**Archivos:** `src/app/api/admin/patients/route.ts`, `src/hooks/usePacientes.ts`, `src/app/(admin)/pacientes/page.tsx`  
**Flujo:** Pacientes → KPI strip "RGPD aceptado"

**Problema:** `consentCount={patients.filter((p) => p.gdpr_consent).length}` — `patients` son solo los 50 registros de la página actual. Con 300 pacientes en DB mostraba "23 con RGPD" cuando eran 280.

**Fix aplicado (3 capas):**

*API (`route.ts`):* Segunda query `SELECT id` con `count: 'exact', head: true` + `.eq('gdpr_consent', true)`. Respeta `accessiblePatientIds` (scoping por profesional). Devuelve `consentCount` en el JSON.

```typescript
let consentQuery = supabase
    .from('patients')
    .select('id', { count: 'exact', head: true })
    .is('deleted_at', null)
    .eq('gdpr_consent', true);
if (accessiblePatientIds) consentQuery = consentQuery.in('id', accessiblePatientIds);
const { count: consentCount } = await consentQuery;
return NextResponse.json({ data, count, consentCount: consentCount ?? 0 });
```

*Hook (`usePacientes.ts`):* Tipo de payload actualizado a `{ data: Patient[]; count: number; consentCount: number }`. Devuelve `consentCount`.

*Page (`pacientes/page.tsx`):* `const consentCount = result?.consentCount ?? 0`. Eliminado `patients.filter(...)`. `isLoadingPatients` ya no se usa (ver H4).

### H3 · "Marcar completada" sin confirmación — CORREGIDO

**Archivo:** `src/app/(admin)/citas/components/AppointmentDetailPanel.tsx:154`  
**Flujo:** Citas → click cita → panel detalle → "Marcar completada"

**Problema:** Un solo click ejecutaba `onUpdateStatus(appointment.id, 'completed')` inmediatamente. Estado `completed` es terminal — `STATUS_TRANSITIONS` no ofrece transición de vuelta. Acción irreversible sin ningún confirm.

**Fix aplicado:**
- Añadido `useState<boolean>` → `showCompleteConfirm`.
- Botón ahora llama `setShowCompleteConfirm(true)`.
- `<ConfirmModal variant="info" title="Marcar como completada" ...>` renderizado en Fragment al mismo nivel que `<aside>`.
- `onConfirm` llama `void onUpdateStatus(appointment.id, 'completed')`.

### H4 · Búsqueda de pacientes destruye la tabla con spinner completo — CORREGIDO

**Archivo:** `src/hooks/usePacientes.ts`  
**Flujo:** Pacientes → escribir en el buscador

**Problema:** Cada búsqueda (tras debounce) cambia la query key → React Query marca `isLoading=true` para la nueva key → el componente hacía early-return con un spinner full-page que destruía la tabla y cerraba el panel de detalle abierto.

**Fix aplicado:**
- Añadido `placeholderData: keepPreviousData` (importado de `@tanstack/react-query`).
- Durante la búsqueda se muestran los datos anteriores mientras llega la respuesta nueva. Tabla visible en todo momento, sin flash de spinner.
- `isLoadingPatients` eliminado de la desestructuración en `pacientes/page.tsx` (ya no se usa el early-return).

### M2 · Tabs semánticamente incorrectos en PatientDetailsPanel — CORREGIDO

**Archivo:** `src/app/(admin)/pacientes/components/PatientDetailsPanel.tsx:498-513`  
**Flujo:** Pacientes → ficha → tabs Datos / Citas / Documentos

**Problema:** Los botones de tab usaban `aria-pressed` (patrón toggle button). Screen readers anunciaban "botón presionado" en lugar de "tab seleccionado 1 de 3". No había `tablist`, `tabpanel` ni asociaciones `aria-controls`/`aria-labelledby`.

**Fix aplicado:**
- Contenedor `.zs-drawer__tabs` recibe `role="tablist"` + `aria-label="Secciones de la ficha del paciente"`.
- Cada botón recibe `role="tab"`, `id="drawer-tab-{key}"`, `aria-selected={activeTab === tab.key}`, `aria-controls="drawer-panel-{key}"`. Eliminado `aria-pressed`.
- Panel `.zs-drawer__body` recibe `role="tabpanel"`, `id="drawer-panel-{activeTab}"`, `aria-labelledby="drawer-tab-{activeTab}"`.

### M3 · `activeTab` no se resetea al cambiar de paciente — CORREGIDO

**Archivo:** `src/app/(admin)/pacientes/components/PatientDetailsPanel.tsx:176`  
**Flujo:** Pacientes → abrir ficha A en tab "Documentos" → click en paciente B

**Problema:** Al cambiar de paciente, el `useEffect` que limpia estado solo reseteaba `inviteSent` y `expandedDocs`. `activeTab` permanecía en "clinico" para el nuevo paciente (que puede tener cero documentos) mostrando un estado vacío confuso.

**Fix aplicado:**
```tsx
// ANTES
useEffect(() => { setInviteSent(false); setExpandedDocs(new Set()); }, [patient.id]);

// DESPUÉS
useEffect(() => { setInviteSent(false); setExpandedDocs(new Set()); setActiveTab('datos'); }, [patient.id]);
```

## E2E — Cobertura faltante recomendada

Los tests existentes en `e2e/` cubren happy paths. Gaps identificados:

| Test faltante | Riesgo detectado |
|---|---|
| Rol profesional → acceso a `/pacientes`, `/servicios`, `/configuracion` denegado | Bypass RBAC no detectado en E2E |
| Submit formulario con campos vacíos → mensajes de error visibles por campo | Regresión de validación client-side |
| Sesión expirada → redirect a `/login` | Flujo de seguridad |
| PDF generation → descarga o apertura en pestaña nueva | Regresión silenciosa del pipeline PDF |
| API 500 en carga de citas → mensaje de error, no pantalla en blanco | Error state coverage |
| Paginación pacientes → página 2 → 3 → atrás | Bug en `onPageChange` no detectado |
| Rango personalizado en `/analitica` (ambas fechas requeridas) | Validación de custom period |
| Bulk confirm → estado final de todas las citas | Flujo de confirmación masiva |

**Problema estructural:** 14 usos de `waitForTimeout(hardcoded_ms)` en `citas.spec.ts` y `pacientes.spec.ts`. Frágil en CI lento o con DB vacía. Migrar a `waitForResponse` / `waitForSelector`.
